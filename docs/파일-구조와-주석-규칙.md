# 파일 구조와 주석 규칙

수업에서 사용한 `08_2_fastapi`처럼 파일을 열면 역할과 처리 순서를 쉽게 이해할 수 있게 작성한다. 함수와 조건문을 우선하고, 필요한 파일만 기능 구현 시 추가한다.

## 1. 파일 구조

현재 파일과 폴더를 기준으로 정리한다. `notebooks/`에는 기초 사용법과 기능별 실습을 작성한다. `0_1`에는 임베딩, `0_3`에는 Jev·OpenAI 사용법, `1_0`에는 의도 분류 실습 코드가 있다. 코드 작성과 실제 실행 검증 여부는 구분한다. 그 밖의 새 파일은 필요한 기능을 구현할 때 추가한다.

### 파일별 책임

- **`main.py`**: 앱과 라우터, 정적 파일 및 서버 수명주기를 연결한다.
- **`routers/test_pages.py`**: `/test/...`의 HTML 화면을 명시적으로 연결한다.
- **`routers/test_samples.py`**: `/test/api/search/...`와 `/test/api/points/...`의 예시·샘플 이미지를 제공한다.
- **나머지 `routers/`**: `/chatbot/...` 처리 요청과 `/test/api/...` 자료·기록 요청을 받아 함수 결과를 돌려준다.
- **`schemas/`**: 요청, 상태 및 내부 데이터의 형식을 정의한다.
- **`services/`**: 모델 호출과 한 턴의 처리 순서를 작성한다.
- **`common/`**: 클라이언트, 프롬프트 및 JSON 저장소처럼 여러 곳에서 사용하는 코드를 둔다.
- **`prompts/`**: 모델에 전달하는 공통 지침과 역할별 지침을 Markdown으로 보관한다.
- **`templates/`와 `static/`**: 화면 구조, 스타일, 브라우저 동작을 각각 HTML·CSS·JavaScript로 나눈다.
- **`notebooks/`**: 기초 사용법과 기능별 함수 실습을 새로 작성한다. `0_1`에는 임베딩, `0_3`에는 Jev·OpenAI 사용법, `1_0`에는 의도 분류 실습 코드가 있다. `0_1`의 FAISS 실습 저장소는 `data/embeddings/practice_0_1/`로 분리해 기존 인덱스를 보존한다.
- **`tests/`**: API, 처리 함수, 저장소, 프런트 동작을 검증하고 예제 입력을 보관한다.

모델 호출과 처리 순서는 `services/`, 데이터 형식은 `schemas/`, 저장 처리는 `common/`의 해당 파일에서 찾는다. 기존 역할에 맞는 파일을 먼저 사용하고 필요한 경우에만 나눈다.

### 새 노트북 작성 순서

라이브러리 설치 안내는 `0_x` 기초 노트북 코드 셀에 `# uv pip install 패키지명 ...` 한 줄 주석으로 작성하고, `1_x` 서비스 연구 노트북에서는 제거한다. 설치는 사용자가 직접 수행하며, 노트북 실습만을 위해 별도 의존성 그룹을 만들거나 `pyproject.toml`을 변경하지 않는다. 노트북에 `load_dotenv()`를 넣지 않고 서버·브라우저를 열지 않는다. 실제 모델 API 호출은 사용자가 승인한 범위에서만 수행하고 키를 출력하거나 저장하지 않는다.

`0_1` 임베딩, `0_2` OCR, `0_3` Jev와 LLM 사용법은 초보자에게 쉬운 작은 예제와 입력·출력으로 짧고 명확하게 작성한다. `0_3`에는 prompt와 structured output 사용법을 포함한다. `0_3`의 기초 사용법 프롬프트는 파일을 불러오지 않고 노트북 코드 셀에 Markdown 형식의 문자열로 직접 작성한다.

새 노트북의 출처·참고에는 현재 `notebooks/`의 내부 참고 노트북만 적는다.

`1_0_의도분류`, `1_1_unknown`, `1_2_상품주문`, `1_3_상품추천`, `1_4_상품검색`, `1_5_정보문의`는 H1 제목 다음 Markdown 셀에 `mermaid` 코드 블록으로 흐름도를 작성하고, 아래 H2 순서를 따른다.

1. 스키마 설정
2. 모델 준비
3. 관련 프롬프트 불러오기
4. 사용자 input 준비
5. 함수 만들기
6. 연결 테스트

도입에는 왜 이 기능이 필요한지, 입력·처리·출력, 짧은 예시를 적는다. 마지막에 "이번 노트북은 ~" 같은 중복 설명을 붙이지 않는다.

각 테스트는 `Input 준비 → 함수 호출 → Output 확인`을 해당 셀에서 모두 보여준다. 공통 모델·스키마·함수 정의는 재사용하되, 테스트 입력은 그 자리에서 명시적으로 만들고 호출 전후 값을 출력한다. "앞 절의 입력을 사용한다"처럼 다른 예제의 입력 변수에 의존하지 않는다. 연속 대화 테스트는 `state`를 유지하되 각 턴의 `text`는 해당 셀에서 직접 명시한다.

출력은 전체 JSON 대신 문장·의도·confidence 등 해당 테스트와 관련된 값을 텍스트로 보여준다. 입력 정보·함수 호출·결과 출력은 빈 줄로 구분해 읽기 쉽게 표시한다. `print` 코드뿐 아니라 승인된 범위에서 실행한 출력도 노트북에 저장한다. 실행하지 않은 셀·검증은 미실행으로 명시하고, 대체 클라이언트 검증과 실제 API 검증을 구분한다.

흐름도는 `flowchart LR`로 가로 방향으로 배치한다. 입력·출력 노드는 회색으로 표시하고, 문구에는 `Input`/`Output`과 경계에서 실제 주고받는 스키마명만 적는다. 상태 처리 구간의 입력·출력은 `SessionState`, 고객 요청 경계의 입력은 `CustomerRequest`로 표시한다. 처리 노드에는 역할 설명과 실제 함수명을 함께 적는다. Python 처리 노드인 `prepare_state`·`save_state`는 파란색으로, Jev 분류 노드는 기본 스타일로 표시한다. 노트북에서 직접 편집할 수 있도록 Mermaid 원문을 유지하고 첨부 SVG로 대체하지 않는다. 흐름도의 함수명은 실제 정의명과 일치시키고, LLM 호출 함수에는 `generate_` 접두사를 붙인다. 단, `1_0`의 확정된 분류 함수명은 `classify_intent(state)`를 사용한다.

각 함수는 작성 → 직접 호출 → 결과 확인 흐름으로 설명한다. `1_x`의 프롬프트는 실제 `.md` 파일에서 읽고 `print`로 내용을 확인한다. 상태 처리 함수는 `SessionState`를 받아 갱신된 `SessionState`를 반환하고, `intent`는 `intent`와 `confidence`를 묶은 `IntentResult`로 둔다. 흐름을 가리는 불필요한 helper 함수는 최소화한다. 필요한 스키마는 해당 노트북 셀에 직접 정의하고, `Field`에는 필드 의미를 설명하는 `description`을 작성한다.

노트북에는 `assert`, `%run`, 프로젝트 루트 탐색·설정, 작업 디렉터리 자동 변경, `sys.path` 보정 코드를 넣지 않는다. 필요한 실행 위치만 짧게 안내한다. 함수 설명과 단계 주석은 아래 규칙을 따른다. 함수 밖의 일반 코드 셀에도 `# 1. 키워드: 설명` 형식의 단계 주석을 작성하고, 셀마다 1부터 실제 처리 순서대로 번호를 매긴다. 실제 코드를 작성하고 실행하기 전까지 작성 틀을 구현 완료나 모델 검증 완료로 표현하지 않는다.

### 의도 분류의 확정 규칙과 적용 범위

매 턴 Jev로 의도를 분류한다. 모델 입력은 `text`, `previous_intent`, `has_image`만 전달하고 대화 기록과 원본 이미지는 보내지 않는다. 이전 `intent`는 참고값이며, `in_progress`를 이유로 분류 호출을 우회하지 않는다. 이전 의도가 주문일 때 "네 맞아요" 같은 후속 답변은 `product_order`로 분류한다. 주문 중이라도 "근의 공식 알려줘"는 `unknown`으로 분류하고, 분명한 새 카페 요청은 새 의도로 분류한다.

`1_0`에서는 고객이 보낸 `CustomerRequest`와 저장할 `SessionState`를 구분한다. `CustomerRequest`는 `session_id`, `customer_info`, `input` 세 필드이고, `SessionState`는 `session_id`, `customer_info`, `input`, `intent`, `previous_intent`, `history` 여섯 필드다. `intent`는 현재 분류 결과인 `IntentResult(intent, confidence)`이고, `previous_intent`는 이전 의도 이름인 `str | None`이다.

`prepare_state(request)`는 노트북 전역 딕셔너리 `state_store`에서 `session_id`의 마지막 스냅샷을 조회해 있으면 복원하고, 없으면 새 상태를 만든다. 직전 `intent`의 이름을 `previous_intent`에 보관하고 이번 `input`으로 교체한다. 이번 `customer_info`가 `None`이 아닐 때만 고객 정보를 갱신하고, 없으면 기존 정보를 유지한다. 이번 고객 메시지도 이 단계에서 `history`에 추가한다.

`classify_intent(state)`는 매 턴 Jev로 분류하고 `state.intent`에 `IntentResult`를 담아 갱신된 상태를 반환한다. Jev에는 `text`, `previous_intent`, `has_image`만 전달하며 고객 정보·`history`·`confidence`·원본 이미지는 전송하지 않는다. `history`는 상태에 보관한다.

`state_store = {}`로 노트북 전역 저장소를 준비한다. 저장 형식은 `{session_id: [State 스냅샷, ...]}`이며, `save_state(state)`는 해당 세션의 목록에 스냅샷을 추가하되 같은 스냅샷을 연속 저장할 때는 중복을 막는다. 저장소는 현재 커널에서 유지되고, 초기화 셀을 다시 실행하거나 커널을 재시작하면 초기화된다. `prepare_state(request)` → `classify_intent(state)` → `save_state(state)`는 각각 상태 준비·분류·저장을 위한 필요한 함수다. 실습에서는 전역 저장소와 가상 고객 자료만 사용한다. 실제 파일 연결은 프롬프트 `.md` 파일 읽기만 유지하며, 상태 파일은 만들거나 읽지 않는다. 기존 서버의 `data/state/` 형식은 바꾸지 않는다. 대화 기록을 보내지 않는 규칙은 이번 의도 분류에 한정하며, 상품 주문 등 다른 기능의 기록 사용까지 금지하지 않는다.

이 정책의 현재 적용 범위는 `1_0_의도분류.ipynb`와 공유 분류 프롬프트다. 이 요청·저장 구조는 `1_0` 연구용이며 서비스·라우터·공통 스키마에는 아직 이관하지 않았다. 별도 구현·검증이 필요하다.

## 2. 주석 규칙

### 한국어로 이유와 흐름 설명

코드를 그대로 읽어 주는 주석보다, 왜 이 처리가 필요한지와 다음 단계에 어떤 정보를 넘기는지 설명한다.

```python
# 알레르기가 없다는 답변과 아직 확인하지 못한 상태를 구분해 읽습니다.
allergies = customer_info.get("allergies")

# 아직 답을 받지 못했다면 추천을 멈추고, 알레르기부터 물어봅니다.
if allergies is None:

    return {"reply": "알레르기가 있는 재료가 있나요?"}
```

### 함수 설명은 입력과 결과가 보이게

모든 Python 함수·메서드에는 한국어 한 줄 docstring을 쓰고, JavaScript 함수와 여러 줄 콜백에는 한 줄 JSDoc을 씁니다. 노트북·테스트·중첩 함수에도 같은 기준을 적용합니다.

초보자가 함수 이름만 보고 짐작하지 않아도, **무엇을 받아서 무엇을 하고 어떤 결과를 주는지** 알 수 있게 씁니다. 인자가 없으면 언제 실행하고 무엇을 바꾸는지 설명합니다. `~합니다`, `~돌려줍니다`, `~확인합니다`처럼 쉬운 존댓말을 사용합니다.

| 모호한 설명 | 입력과 결과가 드러나는 설명 |
|---|---|
| 메뉴를 필터링한다. | 메뉴 목록과 알레르기 재료를 받아, 먹을 수 있는 메뉴만 골라 돌려줍니다. |
| 상태를 준비한다. | 이번 고객의 저장 정보를 불러와, 요청에 담긴 이전 고객 정보를 새 고객 정보로 바꿉니다. |
| 결과를 검증한다. | 모델이 적은 출처가 이번에 읽은 문서인지 확인하고, 다른 출처가 있으면 오류를 냅니다. |
| 실패를 테스트한다. | 파일 저장 중 오류를 발생시켜, 기존 대화 기록이 그대로 남는지 확인합니다. |

실제 함수가 하는 일에 맞게 설명합니다. 반환값이 없는 함수는 무엇을 화면에 표시하거나 파일에 저장하는지 적습니다. 입력·출력 형식을 모두 나열하려고 문장을 길게 늘리거나, 어미만 바꾸는 방식으로 정리하지 않습니다.

```python
def filter_menu(menu, allergies):
    """메뉴 목록과 알레르기 재료를 받아, 먹을 수 있는 메뉴만 골라 돌려줍니다."""
    # 1. 후보 선택: 고객의 알레르기 재료가 들어 있는 메뉴는 추천에서 뺍니다.
    ...
```

```javascript
/** 고객 ID와 세션 ID로 저장 기록을 불러와, 턴별 처리 결과를 화면에 보여줍니다. */
async function loadStateRecords(customerId, sessionId) {
  // 1. 기록 조회: 선택한 고객의 이번 대화에 저장된 처리 결과를 서버에서 가져옵니다.
  ...
}
```

### 단계 주석은 데이터가 이동하는 순서를 설명

함수 내부는 실제 처리 단락마다 빈 줄로 나누고, `# 1. 키워드: 설명` 형식으로 씁니다. JavaScript는 `// 1. 키워드: 설명`을 사용합니다. 단계 번호는 함수마다 1부터 연속으로 매깁니다. 같은 함수의 조건문·반복문 안에서는 이어서 세고, 별도의 중첩 함수나 콜백은 다시 1부터 시작합니다.

단계 설명에는 어떤 데이터를 읽거나 바꾸는지, 왜 그 조건에서 멈추는지, 다음 단계에 무엇을 넘기는지가 드러나게 씁니다. docstring과 똑같은 문장을 반복하지 않습니다. 짧은 함수는 한 단계로 충분하며, 코드 한 줄마다 주석을 붙이지 않습니다. 테스트는 준비 → 실행 → 확인의 흐름으로 묶습니다.

### 긴 단계의 보조 주석과 반환 전 빈 줄

번호가 붙은 한 단계의 코드가 길면, 데이터나 확인 대상이 바뀌는 중간 경계에 `## 설명` 주석을 넣습니다. JavaScript는 `// ## 설명`을 사용합니다. 보조 주석에 번호를 다시 붙이지 않고, 각 줄을 그대로 읽는 설명은 피합니다.

`return` 문 바로 위에는 빈 줄을 넣어 앞선 처리와 반환을 구분합니다. 반환 설명 주석이 바로 앞에 있어도 주석과 `return` 사이에 빈 줄을 둡니다.

```python
def filter_menu(menu, allergies):
    """메뉴 목록과 알레르기 재료를 받아, 먹을 수 있는 메뉴만 골라 돌려줍니다."""
    # 1. 후보 선택: 판매 여부와 알레르기 정보를 확인해 추천 후보를 모읍니다.
    candidates = []
    for item in menu:
        if not item["available"]:
            continue

        ## 재료 정보가 없는 메뉴는 안전하게 판단할 수 없어 추천에서 뺍니다.
        if item["allergens"] is None:
            continue
        if any(allergen in item["allergens"] for allergen in allergies):
            continue
        candidates.append(item)

    return candidates
```

### 중요한 경계에 주석

- 의도 분류: 진행 중인 질문에 대한 답변인지 새 요청인지.
- 이미지 검색: 유사도 점수는 정답 확률이 아니라는 점.
- 쿠폰 처리: OCR 추출 결과를 검증한 뒤 저장한다는 점.
- 추천: 미확인과 없음의 차이, 필수 정보 충족 조건.
- 카페정보문의: 어떤 문서·메뉴 데이터를 답변 근거로 쓰는지.
- TTS: 응답 문장과 고객 음성 설정을 어디에서 합치는지.

한 턴을 실행하는 함수에서는 `# 1. 의도 분류: 현재 질문과 이전 대화를 Jev에 보내, 실행할 기능을 고릅니다.`처럼 순서와 실제 처리 대상을 함께 설명합니다.

### 주석과 실행 기록 구분

주석에는 고정된 규칙과 이유를 적는다. 실제 사용한 모델·프롬프트·조회 데이터·입출력·처리 시간·오류는 실행 기록에 남긴다. 확인하지 않은 성능이나 성공 여부를 주석으로 단정하지 않는다.

프롬프트 파일의 내용은 모델에 전달되는 지침이다. 개발자를 위한 메모를 프롬프트에 섞지 않는다.

### 프런트엔드 주석

Python은 `#`와 docstring, JavaScript는 `//`와 JSDoc, HTML은 `<!-- -->`, CSS는 `/* */`를 사용합니다. 함수·콜백은 위 설명 규칙을 따르고, HTML·CSS는 화면 영역이나 스타일을 나눈 이유가 필요할 때 짧게 설명합니다. 한 줄짜리 단순 콜백을 설명하려고 여러 줄로 늘리지 않습니다.
