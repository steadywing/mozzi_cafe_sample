# 03 상품추천 노트북 설계안

## 목적

사용자 입력과 대화에서 확인한 조건을 보고 모델이 도구를 선택하고, 실제 Python 함수의 결과를 근거로 질문하거나 답변하는 과정을 실습한다. 기존 01·02 노트북처럼 함수를 작성하고 작은 입력으로 직접 실행한 뒤 전체 흐름을 연결한다.

## 접근 방식

- **모델의 실제 function calling — 제안 방식:** 모델이 함수명과 인자를 출력하고 Python이 실행한다. 사용자 요청인 입력에 따른 툴 선택을 직접 확인할 수 있다.
- 키워드별 Python 분기: 구현은 간단하지만 모델이 도구를 선택하는 실습 목적에 맞지 않아 채택하지 않는다.

사용자는 입력에 따른 도구 호출과 고객 ID로 조회한 고객정보 기반의 필터링을 요청했다. 고객정보를 State에 넣는 변경을 반영해 구현한다.

## 고객정보 연결

- `SessionState.customer`에 `CustomerProfile`을 넣는다. 고객 ID로 `customers.json`을 조회하며 이름·출생연도·회원등급·알레르기·선호만 허용한다. 전화번호 등 무관한 정보는 가져오지 않는다.
- 현재 고객 자료에는 알레르기·선호가 없으므로 누락은 `null`로 유지한다. 자료에 없는 건강·취향 정보를 생성하거나 나이·성별에서 추측하지 않는다.
- 저장된 알레르기·선호가 있으면 추천 기본 조건으로 사용하고, 없는 항목만 질문한다. 저장된 알레르기는 추천 도구 인자가 비어 있어도 제외 조건으로 유지한다. 대화에서 추가한 조건은 추천 상태에서 유지하고 선호 변경도 반영한다.
- 의도 분류와 주문 처리의 상태 준비에서 서버가 고객 자료를 조회한다. 기존 고객 ID만 보낸 요청도 허용하며, 없는 고객이면 프로필은 `null`이다. 다른 고객의 프로필이 전달되면 추천 상태를 초기화한다.
- 분류·주문 모델 입력에서는 고객 프로필을 제외한다. 추천 모델에도 필터에 필요한 정보만 전달한다.

## 도구와 처리 규칙

1. `filter_menu`: 메뉴 데이터에서 판매 가능 여부, 알레르기, 지원하는 선호 조건으로 후보를 구한다. 필요한 조건이 미확인이면 부족한 항목을 반환해 모델이 후속 질문을 한다.
2. `analyze_popular_menu`: 주문 항목의 `quantity`를 메뉴별로 합산한다. 기간 미지정은 전체 저장 기간, 기본 상위 개수는 3개다. 적용 기간과 집계 기준을 결과에 포함한다. 원본 고객·주문 식별자는 모델에 전달하지 않는다.
3. 단순한 “뭐가 인기 많아요?”에는 알레르기 질문을 먼저 강제하지 않고 판매 수량 정보를 안내한다. 개인에게 맞춘 추천은 알레르기와 선호를 먼저 확인한다.
4. “우유 알레르기가 있는데 인기 있는 걸 추천해줘”처럼 두 요구가 함께 있으면 알레르기와 선호 확인·필터를 우선하고 해당 후보 안에서 인기를 비교한다. 모델이 넘긴 후보나 조건만 믿어 기존에 확인한 알레르기를 우회하지 않는다.
5. `null`은 미확인, `[]`는 고객이 없다고 명시한 상태로 구분한다. 후속 답변에서 기존 조건은 유지하고 명시적인 수정은 반영한다. 노트북의 대화 상태는 메모리에서 유지하며 원본 고객·주문 파일에 쓰지 않는다.
6. 알레르기가 있으면 관련 알레르겐 메뉴와 재료·알레르기 정보가 미확인인 메뉴를 제외한다. 카페인·당도 조건이 있으면 해당 정보가 미확인인 메뉴도 일치 후보로 간주하지 않는다. 판매 불가 메뉴는 추천하지 않는다.
7. 첫 버전의 선호는 데이터에 연결되는 맛 태그, 당도, 카페인, 카테고리를 중심으로 제한한다. 지원되지 않는 모호한 조건은 추측해 적용하지 않고 확인한다.
8. 주문 데이터에는 취소·완료 상태가 없으므로 “저장된 주문 데이터의 수량 기준”이라고 설명한다. 옵션 주문 이력으로 메뉴 기본 알레르기·카페인 정보를 바꾸지 않는다.

## 노트북 구성

1. 준비: 기존과 같은 `OpenAI()`·`OPENAI_MODEL` 설정, `../data/`·`../prompts/` 읽기. 작업 위치는 `notebooks`로 안내한다.
2. 메뉴·주문 데이터 구조 확인.
3. 필터 함수 작성 → 직접 호출 → 결과 확인.
4. 인기 분석 함수 작성 → 직접 호출 → 결과 확인.
5. 도구 정의와 Markdown 프롬프트 준비.
6. 사용자 입력 → 모델의 함수명·인자 확인 → Python 실행 → 도구 결과 전달 → 최종 답변을 셀별로 확인.
7. 전체 과정을 연결하는 짧은 함수와 대화 상태 작성. 추가 도구 호출이 있으면 결과를 전달하고 반복하며, 호출 횟수에 상한을 둔다.
8. 조건 부족 질문·후속 답변·조건 수정·인기 조회·개인 조건과 인기 결합·후보 없음 예제를 직접 실행.
9. 클라이언트 종료.

## 파일 범위

- `schemas/session_state.py`, `common/customer_store.py`: 고객 프로필과 조회.
- `services/intent_classifier.py`, `services/product_order.py`: 고객 프로필 준비와 불필요한 모델 입력 제외.
- `notebooks/03_상품추천.ipynb`
- `prompts/recommendation_tools.md`: 도구 선택, 후속 질문, 상태 해석, 근거 기반 답변 지침.
- 필요 시 관련 Python 함수·도구 연결의 검증을 위한 `tests/` 파일. 노트북에는 `assert`를 넣지 않는다.

기존 API 경로·화면·프롬프트·메뉴·고객·주문 데이터는 수정하지 않는다. 새 프레임워크나 패키지는 추가하지 않는다.

## 검증

- 필터에서 알레르기 제외, 미확인 값, 판매 불가, 조건 수정, 후보 없음을 확인한다.
- 인기 집계는 실제 주문 수량과 비교하고 개인 조건이 인기 추천에서도 유지되는지 확인한다.
- 대체 모델 응답으로 함수 선택·결과 반환·후속 호출 연결을 검증한다. 실제 모델 호출과 구분해 보고한다.
- 노트북 코드 문법과 셀 실행 순서, 한국어 docstring·단계 주석, 프롬프트 외부화, 금지된 설정 코드 유무를 확인한다.
