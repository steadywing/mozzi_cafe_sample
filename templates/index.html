01전체 처리 구조

의도 분류 API는 세션 상태를 준비하고 매 턴 Jev로 분류하며, unknown일 때 확인 답변을 생성합니다. 주문·추천·검색·문의·포인트 적립은 별도 실습 API로 실행하며, 분류 결과가 이 API들을 자동 호출하지는 않습니다. 화면은 /test/..., 챗봇 처리는 /chatbot/..., 테스트 자료는 /test/api/...에서 확인합니다.

실선 화살표는 같은 API 안의 실행 순서, 점선 화살표는 고객 확인 뒤 별도 요청으로 이어지는 순서입니다. 의도 분류와 기능별 실습은 각각 별도 요청으로 시작하며, 후속 입력의 보관 방식은 기능마다 다릅니다.

02포트폴리오를 위한 고민

무엇을 만들었는지에 더해, 왜 선택했고 어떻게 검증했는지 보여줍니다.

01모델 선정

  • 영수증 OCR: 후보와 선택 이유

    영수증에서 주문번호·날짜·결제금액을 읽기 위해 전용 OCR과 이미지 입력을 받는 멀티모달 모델을 후보로 비교할 수 있습니다. 예를 들어 Google Cloud Vision OCR은 문자를 읽고, Gemini는 이미지를 보고 필요한 항목을 구조화하는 방식입니다. 현재 실습에는 Gemini 2.5 Flash를 사용해 영수증에서 필요한 값을 JSON으로 추출했습니다.

    영수증 사진에서 글자를 읽는 것뿐 아니라 검증에 필요한 필드를 나누어야 했기 때문에 이 방식을 선택했습니다. 예제에서 주문번호와 결제금액을 읽어 주문 자료와 비교했습니다.

  • 이미지 임베딩: 후보와 선택 이유

    고객이 메뉴 이름을 몰라도 사진으로 검색할 수 있도록 이미지 임베딩을 사용했습니다. 비교 후보의 예로 CLIP·SigLIP 계열과 EmbeddingGemma를 놓고 이미지·텍스트 입력 지원, 검색 결과, 실행 환경을 살펴볼 수 있습니다. 현재 google/embeddinggemma-2로 메뉴 사진을 벡터로 만들어 저장하고, 고객 사진과의 유사도로 후보를 찾습니다.

    이 모델은 이미지와 텍스트를 검색 입력으로 다루는 실습 흐름에 맞춰 사용했습니다. 실제 예제에서는 한입 베어 문 딸기 모찌 사진을 검색해 딸기 찹쌀모찌가 첫 후보로 나왔습니다.

  • 검토와 실험 결과를 구분하기

    위의 다른 모델은 비교할 수 있는 후보 예시입니다. 프로젝트에 후보 모델별 동일 조건 성능·속도·비용 비교 기록은 없으므로, 실제로 비교해 더 우수했다고 주장하지 않습니다. 포트폴리오에서는 앞으로 같은 영수증·검색 사진으로 읽기 정확도와 후보 결과를 비교할 수 있습니다.

02프롬프트 관리

  • AI와 함께 테스트 사례를 만들고 평가하기

    먼저 AI에게 기능에서 확인해야 할 정상·후속 답변·예외 상황의 테스트 케이스와 기대 결과를 제안해 달라고 요청합니다. 제가 사례와 기대 결과가 적절한지 검토하고, 테스트보드에서 실제 모델 입력·프롬프트·결과를 확인합니다. 그 결과를 보며 AI와 어떤 분류 기준이나 표현을 고칠지 논의합니다.

  • 같은 사례로 프롬프트 다시 확인하기

    예를 들어 주문 중 “네, 맞아요”는 주문의 후속 답변, “주차할 수 있나요?”는 새로운 정보문의로 기대합니다. 이전 의도 없이 “네, 맞아요”만 보낸 경우와 서로 다른 요청이 섞인 경우도 함께 살펴봅니다. 개선한 프롬프트를 적용한 뒤 같은 입력을 다시 실행해 결과를 비교하며, 실제 비교 기록과 앞으로 할 평가를 구분합니다.

  • 지침과 결과를 확인 가능한 형태로 관리하기

    프롬프트는 기능별 Markdown 파일로 나누고 테스트보드와 노트북에서 실제 전달 내용을 확인합니다. 추천 답변에서 알레르기에 대해 단정적인 표현이 나온 사례를 보고, AI와 개선점을 검토해 안전을 보장하지 않고 매장에 확인하도록 지침을 보완했습니다. 사람의 검토와 반복 평가가 필요합니다.

03정보의 연결과 데이터 관리

  • 챗봇에 필요한 데이터를 어떻게 마련했는가?

    실제 매장·고객 자료 대신 수업용 가상 데이터를 만들었습니다. 메뉴 17개의 이름·가격·재료·알레르기·판매 여부는 data/menu.json에, 운영시간·위치·매장 이용 안내는 data/cafe_docs/의 문서로 나누었습니다. 가상 고객 10명의 포인트는 data/customers.json, 주문 40건은 data/orders.json에 둡니다.

  • 이미지와 검색 자료를 어디에 배치했는가?

    메뉴 기준 사진은 data/menu_images/, 촬영 각도와 조명을 달리한 검색 테스트 이미지는 data/search_images/, 영수증 샘플 3장은 data/sample_receipts/에 두었습니다. 검색할 때 이미지 벡터와 메뉴 ID 순서를 연결할 수 있도록 색인과 목록은 data/embeddings/에 함께 저장합니다. 검색 이미지와 영수증은 AI로 만든 가상 샘플입니다.

  • 어떤 정보를 연결하고 구분하는가?

    정보문의 답변에는 관련 안내 문서를, 추천에는 고객이 말한 알레르기·선호와 메뉴 재료를, 포인트 검증에는 영수증과 주문 기록을 연결합니다. 알레르기 미확인(null)과 없음([])은 구분하고 구매 이력으로 알레르기를 추정하지 않습니다. 테스트 사례와 세션 예시는 tests/fixtures/에 둡니다. 실제 운영에는 영수증 처리 기록의 지속 저장과 적립 기준이 추가로 필요합니다.
